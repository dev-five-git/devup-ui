# 스타일 저장소

Devup UI는 하나의 저장소에 스타일을 저장하고 조회하여 중복을 제거하며, 동일한 스타일 선언에는 같은 원자적 클래스를 재사용합니다.

이 문서에서는 중복 제거 원리, 단일 저장소가 필요한 이유와 빌드 순서와의 관계, 단일 CSS 출력 옵션, 페이지별 CSS 분할, 그리고 결정적인 순서를 갖는 키–값 스타일 저장소를 설명합니다.

### 동작 방식

- 같은 스타일이 여러 곳에 나타나더라도 원자적 클래스는 정확히 하나만 생성됩니다(중복 없음).
- 스타일이 이미 저장소에 있으면 기존 클래스를 재사용합니다. 없으면 새 클래스를 생성해 등록합니다.

### 단일 저장소가 필요한 이유

- 중복 제거와 재사용을 보장하려면 빌드 파이프라인에 스타일 저장소가 정확히 하나만 있어야 합니다.
- 저장소가 여러 개이면 중복 감지가 분산되어, 같은 스타일이 서로 다른 클래스 이름으로 생성될 수 있습니다.

## 단일 CSS 옵션

- `single css`: 생성된 모든 스타일을 하나의 CSS 출력 파일로 내보냅니다.
- 기본값은 `false`입니다.
- 장점: 로딩 경로가 단순해지고 브라우저 캐시 이점을 극대화합니다.
- 단점: 앱이 매우 크거나 페이지마다 스타일이 크게 다르면 초기 로딩이 늘어날 수 있습니다.

### 스타일 순서와 키–값 저장소

- 저장소는 키–값 모델을 사용합니다. 스타일 시그니처가 키이고, 생성된 클래스 이름과 규칙이 값입니다.
- 규칙 순서는 빌드 중 발견된 순서를 따릅니다. 우선순위가 같은 규칙은 출력을 예측할 수 있도록 결정적으로 병합됩니다.

### 페이지별 CSS 분할(선택 사항)

- 페이지별로 CSS를 분할하면 해당 페이지에 필요한 규칙만 불러올 수 있습니다.
- 대규모 애플리케이션에서는 초기 로딩 시간이 개선될 수 있습니다. 단일 전역 CSS만 사용하면 일부 페이지의 초기 로딩이 제약될 수 있다는 점을 염두에 두는 것이 좋습니다.
- 과도하게 분할하면 네트워크 요청이 늘고 캐시가 분산될 수 있습니다. 앱 규모와 탐색 패턴에 맞게 균형을 맞추세요.

### 제로 런타임과의 관계

- 스타일 저장소는 컴파일 시점에 처리되므로, 클라이언트 측 스타일 엔진이나 추가 런타임 계산이 필요하지 않습니다.
- 배경과 설계 근거는 제로 런타임 가이드를 참고하세요: [제로 런타임](/docs/core-concepts/zero-runtime)
