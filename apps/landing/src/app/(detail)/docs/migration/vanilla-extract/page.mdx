# vanilla-extract

## Stylesheet files

Inside `.css.ts` / `.css.js` — the only place vanilla-extract allows its APIs — Devup UI evaluates the module and replaces every call with its generated output. The whole surface works there: `style`, `globalStyle`, `keyframes`, `styleVariants`, `fontFace`, `globalFontFace`, `createVar`, `fallbackVar`, `createTheme`, `createGlobalTheme`, `createThemeContract`, `createGlobalThemeContract`, `assignVars`, `layer`, `globalLayer`, `createContainer`. Generated names — custom properties, containers, layers, theme classes, font families — are unique to each stylesheet, and layers keep the order they are declared in.

```ts
// theme.css.ts
import { createTheme, createThemeContract, style } from '@vanilla-extract/css'

export const vars = createThemeContract({ colors: { bg: null }, space: null })
export const light = createTheme(vars, {
  colors: { bg: 'white' },
  space: '8px',
})
export const box = style({ background: vars.colors.bg })
export const base = style({ padding: 8 })
```

Numbers keep vanilla-extract's meaning, here and in ordinary modules: `padding: 8` is `8px`, and unitless properties such as `lineHeight` or `zIndex` stay as written. As in vanilla-extract, a number for a time gets `px` too (`transitionDuration: 300` is `300px`, which browsers ignore), so write times with their unit: `transitionDuration: '300ms'`.

An array as a property's value declares each value as a fallback, as vanilla-extract does: `height: ['100vh', '100dvh']` is `height:100vh;height:100dvh`, values written as they are. This holds in stylesheets that import `@vanilla-extract/css` and in ordinary modules; a stylesheet using Devup UI's own `style` keeps responsive arrays, and Devup UI shorthands such as `p` read an array as breakpoints everywhere.

A `debugId` names what `createVar`, `createContainer`, `layer`, `fontFace` and `createTheme` generate. Class names come from Devup UI, so with the plugin's `debug` option `style(rule, 'root')` adds a class such as `root-0-0` next to its readable classes, and `styleVariants(variants, 'tone')` adds `tone_primary-0-1` to the `primary` variant, the way vanilla-extract names them. Those classes style nothing, and a build without `debug` leaves them out. `keyframes` accepts a `debugId` and ignores it: its name comes from Devup UI, readable with `debug`.

A stylesheet can import other stylesheets and ordinary modules — ES modules or CommonJS — resolved like the bundler resolves them (relative paths, `tsconfig` `paths` and packages). An imported stylesheet is extracted the way the bundler extracts it, so the class names and custom properties it exports are the ones its own CSS uses, and the importer keeps importing it so that CSS is loaded:

```ts
// tokens.ts
export const PRIMARY = 'blue'
```

```ts
// button.css.ts
import { style } from '@vanilla-extract/css'

import { base, vars } from './theme.css'
import { PRIMARY } from './tokens'

export const button = style([base, { color: PRIMARY, margin: vars.space }])
```

A change to an imported file rebuilds the stylesheets importing it. Import cycles behave as in ES modules: they work as long as neither side reads the other before it has been evaluated, and reading too early is a build error naming the binding and the module.

A stylesheet that throws while it is evaluated — an import that does not resolve, a property read on `undefined` — is a build error carrying that exception, rather than output that still calls `style()` at runtime.

## Ordinary modules

Named imports of `style`, `globalStyle` and `keyframes` also resolve in `.ts` /
`.tsx`, mapped onto their Devup UI counterparts. Literal rule objects compile
there without evaluating the whole module:

```tsx
import { globalStyle, style } from '@vanilla-extract/css'

export const a = style({ color: 'red' })
globalStyle('body', { margin: 0 })
```

```text
import "@devup-ui/react/devup-ui.css";
export const a = "a";
;
```

With an empty theme, the same probe emits:

```text
/*! devup-ui v1.0.82, | Apache License 2.0 | https://devup-ui.com */@layer b;@layer b{body{margin:0}}.a{color:red}
```

Generated names depend on the class prefix and extraction state. The
vanilla-extract API import is removed, but the generated CSS import remains.

`globalStyle(selector, rules)` keeps vanilla-extract's two-argument shape; the extractor folds the selector back into the object `globalCss` takes.

When the build knows the composed styles, `style([base, { ... }])` keeps
non-conflicting declarations and lets the later part win per property,
selector, breakpoint, and layer, as described in
[Supported Syntax & Limitations](/docs/limitations). For example:

```ts
import { style } from '@vanilla-extract/css'

const base = style({ color: 'red', padding: 8 })
export const button = style([base, { color: 'blue' }])
```

Extracted code:

```text
import "@devup-ui/react/devup-ui.css";
const base = "a b";
export const button = "b c";
```

Generated CSS:

```text
/*! devup-ui v1.0.82, | Apache License 2.0 | https://devup-ui.com */.c{color:blue}.a{color:red}.b{padding:8px}
```

`button` does not include the conflicting red class. Unknown external classes
still follow the CSS cascade; class-name string order is not an override rule.

Ordinary-module extraction does **not** execute a vanilla-extract theme contract
declared in that module to discover its generated custom properties. Declare
contracts and themes in `.css.ts` / `.css.js`. For example, the stylesheet
example at the top of this page is not valid if saved as an ordinary `theme.ts`
module:

```ts
// theme.ts (not a stylesheet file)
import { createTheme, createThemeContract, style } from '@vanilla-extract/css'

const vars = createThemeContract({ colors: { bg: null } })
export const light = createTheme(vars, { colors: { bg: 'white' } })
export const box = style({ background: vars.colors.bg })
```

The probe locates the call at line 6, column 20 and reports this message:

```text
`css()` cannot use `vars.colors.bg` at build time: its values must be literals, theme tokens or constants, or be computed from them
```

An ordinary module can import what a stylesheet exports, though. The build
extracts the imported `.css.ts` / `.css.js` the way the bundler extracts it and
reads its exports as the literals its own CSS uses: the vars objects of
`createThemeContract`, `createTheme` and `createGlobalTheme`, theme classes,
`createVar` variables and `style` class names. So the two-file example above
also works as an ordinary module:

```ts
// button.ts (not a stylesheet file)
import { style } from '@vanilla-extract/css'

import { base, vars } from './theme.css'
import { PRIMARY } from './tokens'

export const button = style([base, { color: PRIMARY, margin: vars.space }])
```

`vars.space` reads as the custom property `theme.css.ts` declares,
`margin: var(--space-…)`, and `base` contributes the class `theme.css.ts`
generates. The import of `./theme.css` stays, so its CSS is loaded, and a
change to it — or to a file it reads — rebuilds `button.ts`.

Only the stylesheet's exports are read this way. A stylesheet that throws while
it is extracted, or an export the build cannot read as a literal, still
reports the read as a located error:

```text
`css()` cannot use `vars.space` at build time: its values must be literals, theme tokens or constants, or be computed from them
```

The remaining APIs stay imported from `@vanilla-extract/css` outside a
stylesheet file. For example, `createVar()` and `styleVariants()` remain calls
to that package even when a `style()` call in the same module is transformed.
They are not evaluated by the ordinary-module extraction path.

Moving those calls into a `.css.ts` file — where vanilla-extract wants them anyway — removes the dependency.

## `@vanilla-extract/css-utils`

`calc` builds the same strings `@vanilla-extract/css-utils` does, so the package need not be installed. `calc.add`, `calc.subtract`, `calc.multiply`, `calc.divide` and `calc.negate` give a string; `calc(x)` gives an expression whose `add`, `subtract`, `multiply`, `divide` and `negate` chain, and which is a CSS value once `.toString()` is called or it is interpolated in a template. As in the package, an operand that is itself a `calc` is only parenthesized:

```ts
import { calc } from '@vanilla-extract/css-utils'

calc.add('100%', '-4px') // 'calc(100% + -4px)'
calc.negate('4px') // 'calc(4px * -1)'
calc('10px').add('5px').multiply(2).toString() // 'calc((10px + 5px) * 2)'
calc.add(calc.multiply('2px', 3), '1px') // 'calc((2px * 3) + 1px)'
```

A `.css.ts` stylesheet evaluates `calc`, so its operands can be anything the stylesheet computes, such as `vars.space.md` or a `createVar()`. Any other module is not evaluated: each `calc` there is written as the string it gives, so its operands must be literals, module-level `const`s holding a literal, or other `calc` results. Anything else is a build error at the operand, as is a `calc` read without being called, a `calc(x)` used as a value without `.toString()`, a namespace or default import, and a `require()` or re-export of the package. To use the package itself, set `importAliases: { '@vanilla-extract/css-utils': false }`.

## Unsupported packages and APIs

While `@vanilla-extract/css` is aliased, `@vanilla-extract/recipes`, `@vanilla-extract/sprinkles` and `@vanilla-extract/dynamic` are build errors however a file loads them — an import, `export … from`, `export *`, `require()` or `import()` — since what they generate or assign would never reach the stylesheet. `globalKeyframes()` is a build error too: Devup UI names every keyframes itself, so declare them with `keyframes()` and use the name it returns. To keep any of these, set `importAliases: { '@vanilla-extract/css': false }` and build with the vanilla-extract plugin.
