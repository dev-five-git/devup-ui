# StyleX

`@stylexjs/stylex` needs no alias configuration — the extractor recognises the package directly, through the default import, a namespace import, or named imports.

## Styles and props

`create()` becomes a namespace-to-class-name object and `props()` becomes the attributes to spread:

```tsx
import stylex from '@stylexjs/stylex'

const styles = stylex.create({
  base: { display: 'inline-block' },
})
const colors = stylex.create({ red: { color: 'red' }, blue: { color: 'blue' } })

const el = <div {...stylex.props(styles.base, colors[color])} />
```

```tsx
const styles = { base: 'a' }
const colors = { red: 'b', blue: 'c' }

const el = <div {...{ className: `a ${colors[color] || ''}` }} />
```

Computed access such as `colors[color]` is resolved against the object the `create()` call was rewritten into, so every generated atom stays reachable. `stylex.attrs()` behaves the same but emits `class` instead of `className`.

Numbers get the unit StyleX gives them: `fontSize: 16` is `16px`, `transitionDuration: 300` is `300ms`, and unitless properties such as `lineHeight` stay as written. A number passed to a dynamic style gets the same unit at runtime.

Accepted argument shapes:

```tsx
stylex.props(styles.base) // member access
stylex.props(styles['base']) // literal key
stylex.props(colors[color]) // runtime key
stylex.props([styles.a, styles.b]) // StyleXArray, nestable
stylex.props(on && styles.active) // conditional
stylex.props(styles?.base) // optional chaining
```

## Shorthands and `styleResolution`

StyleX's babel plugin decides between a shorthand and the longhands it covers with its `styleResolution` option. Pass the same option to the Devup UI plugin:

```ts
// vite.config.ts (every plugin takes the same option)
DevupUI({ stylex: { styleResolution: 'application-order' } })
```

| `styleResolution`                  | What wins                                                                |
| ---------------------------------- | ------------------------------------------------------------------------ |
| `'property-specificity'` (default) | A longhand beats a shorthand, whatever order they apply in               |
| `'application-order'`              | The property applied last, shorthand or not                              |
| `'legacy-expand-shorthands'`       | No shorthand is left: each one is split into its longhands at build time |

Whatever the policy, in one `props()` or `attrs()` call a later style replaces an earlier one for the same property and condition: `stylex.props(colors.red, colors.blue)` keeps only the blue class.

```tsx
const styles = stylex.create({
  top: { paddingTop: '1px' },
  pad: { padding: '2px' },
})

const el = <div {...stylex.props(styles.top, styles.pad)} />
```

- `'property-specificity'` keeps both classes and writes `padding-top` after `padding` in the stylesheet, so `padding-top: 1px` wins.
- `'application-order'` gives `padding` `null` resets for the longhands it covers, as StyleX does, so the later `padding` removes `padding-top`. In the other order both stay and `padding-top` wins.
- `'legacy-expand-shorthands'` turns `padding: '1px 2px'` into `padding-top`, `padding-inline-end`, `padding-bottom` and `padding-inline-start`, which merge key by key like any longhand.

The two non-default policies read StyleX's own shorthand tables, including its aliases (`marginStart` is `margin-inline-start`, `blockSize` is `height`), and apply to static `create()` namespaces only. A shorthand there cannot take `firstThatWorks()` fallbacks, and `application-order` rejects `all`, as StyleX does; both are build errors naming the key. Dynamic (arrow-function) namespaces keep their shorthands as written, and `float`/`clear` keep logical values such as `inline-start` as written, because StyleX's polyfill for them relies on its own runtime variables. An unknown `styleResolution` is a configuration error when the plugin is created. Devup UI's own APIs (`css()`, `styled`, `Box` props) ignore the option: there a shorthand written after a longhand wins.

## Variables and themes

```tsx
const colors = stylex.defineVars({ primary: 'blue', secondary: 'grey' })
const dark = stylex.createTheme(colors, { primary: 'navy' })
const styles = stylex.create({ box: { color: colors.primary } })

const el = <div {...stylex.props(dark, styles.box)} />
```

```css
:root {
  --a: blue;
  --b: grey;
}
.c {
  --a: navy;
}
.d {
  color: var(--a);
}
```

```tsx
const colors = { primary: 'var(--a)', secondary: 'var(--b)' }
const dark = 'c'
const styles = { box: 'd' }
const el = <div {...{ className: 'c d' }} />
```

`createThemeContract()` produces the same references without publishing a `:root` block, and `defineConsts()` inlines its values into the `create()` calls that read them.

A variable or theme value can depend on at-rules, with an optional `types.*()` wrapper. Each set of conditions becomes one block after the unconditional values, and nested conditions come after the ones they refine, so the more specific value wins:

```tsx
const DARK = '@media (prefers-color-scheme: dark)'

const colors = stylex.defineVars({
  text: { default: 'black', [DARK]: 'white' },
  accent: stylex.types.color({ default: 'blue', [DARK]: 'lightblue' }),
})
const dracula = stylex.createTheme(colors, {
  text: { default: 'purple', [DARK]: 'pink' },
})
```

```css
@property --b {
  syntax: '<color>';
  inherits: true;
  initial-value: blue;
}
:root {
  --a: black;
  --b: blue;
}
@media (prefers-color-scheme: dark) {
  :root {
    --a: white;
    --b: lightblue;
  }
}
.c {
  --a: purple;
}
@media (prefers-color-scheme: dark) {
  .c {
    --a: pink;
  }
}
```

Conditions are `default`, `@media`, `@supports` and `@container` keys, and `null` leaves a variable unset under its condition. A value that is not static is a build error naming it; pseudo-class keys count as not static, because a variable is set on `:root` or a theme class, not on the element being styled.

A `types.*()` wrapper registers the variable with `@property`, its `default` as the initial value, so it animates and interpolates as that type. A typed variable without a `default`, a `types.integer()` given a fraction, and an unknown `types.*` helper are build errors. A key that is already a custom property name, such as `'--global'`, keeps that name, and `colors['--global']` reads it.

As StyleX requires, variables usually live in a `.stylex.ts` file and are imported where they are used. Imports resolve like the bundler resolves them, and the importing file reads the same custom properties, theme classes and constants that the defining file generates:

```tsx
// tokens.stylex.ts
export const colors = stylex.defineVars({ primary: 'blue' })
export const spacing = stylex.defineConsts({ gap: '8px' })
```

```tsx
// Button.tsx
import { colors, spacing } from './tokens.stylex'

const dark = stylex.createTheme(colors, { primary: 'navy' })
const styles = stylex.create({
  box: { color: colors.primary, marginTop: spacing.gap },
})
```

A value in `create()` that this file's own functions compute from constants with exact built-ins, such as `double(SIZE)`, is computed at build time; another module's code never runs, and code whose result is not certain (`Date`, `Math.random`, `Math.sin`, locale methods, `new`, `this`...) is not run. A value only known at runtime, such as a prop or a state, is a build error naming it, as is anything `create()`, `defineVars()`, `defineConsts()`, `createTheme()`, `keyframes()`, `positionTry()` or `viewTransitionClass()` cannot read (a spread, a computed key that is not a constant, a non-object argument). A computed condition key may read a constant, as `[constants.wide]` naming a `defineConsts()` query. Pass runtime values through a dynamic style (`(color) => ({ color })`), which becomes a CSS variable instead; a dynamic style may set its parameters under conditions too, as `(size) => ({ width: { default: 100, ':hover': size } })`, each condition taking its own variable.

`stylex.props()` accepts styles compiled elsewhere — a `style` prop a parent passes, a spread, another module's namespaces — and joins their class names at runtime; namespaces of this file resolve at build time.

## At-rules

```tsx
const fallback = stylex.positionTry({ top: '0', insetBlockEnd: 'auto' })
const transition = stylex.viewTransitionClass({
  old: { animationDuration: '300ms' },
  new: { animationDuration: '150ms' },
})
const styles = stylex.create({
  popover: { positionTryFallbacks: fallback, anchorName: '--trigger' },
  card: { viewTransitionClass: transition },
})
```

```css
@position-try --a {
  top: 0;
  inset-block-end: auto;
}
::view-transition-old(*.b) {
  animation-duration: 300ms;
}
::view-transition-new(*.b) {
  animation-duration: 150ms;
}
```

The bindings read as their names in `create()`, and a dashed ident on a property that names an anchor, a timeline or a `@position-try` rule (`anchorName: '--trigger'`) stays a name instead of becoming `var(--trigger)`. `viewTransitionClass()` takes the groups `group`, `imagePair`, `old` and `new`; any other key is a build error.

## Value helpers

`firstThatWorks()` emits its fallbacks in CSS order and `types.*()` unwraps to the inner value in `create()` (and registers `@property` in `defineVars()`). Values may be plain literals, condition objects (`{ default, ':hover', '@media ...' }`), or arrow functions, which become CSS variables bound at the call site.

`include()` is not part of the current StyleX API. StyleX deprecated it and current `@stylexjs/stylex` releases no longer export it; StyleX composes namespaces by passing several of them to `props()` instead. Only the `@devup-ui/react/compat/stylex` declarations still type it. Devup UI still compiles the legacy `...stylex.include(base.root)` spread inside `create()` as a Devup UI extension, so code written for older StyleX keeps building. The argument must be a namespace that a `create()` call earlier in the same file defines; anything else is a build error. The spread merges the included namespace's keys where it is written: a key written after the `include()` overrides the included one, so `{ ...stylex.include(base.root), color: 'blue' }` keeps only the blue class for `color`, and a later `include()` likewise overrides the keys before it. This is resolved at build time, including when the namespace is passed to `props()`. A dynamic (arrow function) namespace has no keys to merge, so its classes are only added before the namespace's own. Passing both namespaces to `props()` (`stylex.props(base.root, styles.fancy)`) composes them the same way in StyleX and Devup UI.

## Unsupported APIs

Devup UI compiles `create`, `props`, `attrs`, `keyframes`, `defineVars`, `createTheme`, `createThemeContract`, `defineConsts`, `positionTry`, `viewTransitionClass`, `firstThatWorks` and `types`, plus the legacy `include` described above. Any other export of `@stylexjs/stylex` (`when`, `env`, `defaultMarker`, ...) would stay a StyleX call that throws at runtime, so importing it or reading it from the package is a build error naming it.
