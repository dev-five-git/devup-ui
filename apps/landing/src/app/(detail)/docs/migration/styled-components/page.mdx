# styled-components & Emotion

Both libraries are covered by the same default aliases, and every spelling of `styled` compiles to a static component.

## Supported call shapes

```tsx
import styled from 'styled-components'

const A = styled.div`
  color: red;
`
const B = styled('div')`
  color: red;
`
const C = styled.div({ bg: 'red' })
const D = styled('div')({ bg: 'red' })
const E = styled(Component)({ bg: 'red' })
const F = styled('div', { bg: 'red' })
const G = styled(motion.div)`
  color: red;
`
const H = styled(forwardRef(Field))({ bg: 'red' })
const I = styled['div']`
  color: red;
`
```

Any base renders: a tag, a component, a member such as `motion.div`, or any other value, read once where the component is declared. A tag may also be read as a literal key, `styled['div']` or ``styled[`div`]``, which builds what `styled.div` does, `.attrs` and `.withConfig` included; a key the build cannot read (`styled[tag]`) or one `styled.` could not spell (`styled['my-element']`) is a build error. `null`, numbers, booleans and `undefined` never render, so they are build errors, as is a `styled` left uncompiled (`styled('div')` never given styles, `styled.div` exported bare): its import is removed, and that code would throw at runtime.

A `keyframes` or `css` result held in a `const` of the same file is a build-time value, so `` css`animation: ${fadeIn} 1s;` `` and `styled.div({ ['.' + card + ':hover &']: { margin: 0 } })` work. In CSS text a class standing where a declaration would is a mixin, composed with the component's class. One imported from another module is not: its name is only known once that file is built, so declare it where it is used.

Object styles follow the libraries: several style arguments, or an array of them, merge into one rule set where a later declaration replaces an earlier one and nested rules merge; Emotion's options argument (`styled('div', { shouldForwardProp })(...)`) is accepted, and its `shouldForwardProp` is evaluated at build time. Numbers mean pixels as they do in Emotion and styled-components — `padding: 8` is `8px`, unitless properties such as `lineHeight` stay as written — while Devup UI shorthands such as `p` keep the spacing scale.

An array as a property's value follows the libraries too, not Devup UI's breakpoints. In Emotion it declares each value in turn as fallbacks (`height: ['100vh', '100dvh']` is `height:100vh;height:100dvh`), skipping `null`, `undefined` and booleans; when its first value is not a string Emotion writes no usable declaration (`margin: [4]`), so nothing is declared. styled-components writes the values joined by commas as one declaration (`fontFamily: ['Arial', 'sans-serif']` is `font-family:Arial,sans-serif`). Devup UI shorthands such as `p` keep reading an array as breakpoints, and so does `css()` from `@devup-ui/react`.

A key holding an object that names no style property is a nested selector, as in the libraries: `{ span: { color: 'blue' } }` is `.a span{color:blue}`, `{ 'h1, h2': { margin: 0 } }` gives `.b h1` and `.b h2`, a key starting with `:`, `::` or `[` applies to the component, and `&` says where the component goes. A pseudo-class or pseudo-element name written alone, such as `hover` or `before`, is that selector as in Devup UI's [`selectors`](/docs/api/selector) rather than a `<hover>` element, and a Devup UI shorthand such as `p` stays a property, so write `'& p'` to select paragraphs.

A style argument can be conditional — `cond && { ... }`, `cond ? { ... } : { ... }`, `value || { ... }` or `value ?? { ... }`, in `styled` as in `css`. Each property it sets becomes a per-property ternary over what came before (`color: cond ? 'blue' : 'red'`), so the result does not depend on the order atomic classes land in the stylesheet; a conditional class joins as `cond ? cls : ''`, and the left side of `||` / `??` joins only when it is a string, as the libraries skip other values. Classes passed beside rule objects compose in `styled` as in `css`.

A style argument that cannot be known at build time — a function call the build cannot run, a spread or a computed key it cannot compute — is a build error naming it, rather than a silently missing style; a spread, a selector value or a computed key the module computes (`styled.div({ ...cardStyles(), _hover: hoverStyles })`) is computed, while the other values stay CSS variables set at runtime. An object constant, declared in the file or imported, reads as if written in place: `styled.div(baseStyles)`, `styled.div({ ...baseStyles, color: 'red' })`. A single argument that is not a rule object composes as a class, as several do; one holding rules the module computes (`const base = makeStyles()`, `styled.div(base)`) applies those rules. In the object form a value may read the theme (`(p) => p.theme.brand`); any other function of the props is a build error — write it in a template (`${(p) => p.color}`), where it becomes a CSS variable.

A styled callback cannot return a class name known only at runtime (`styled.div(p => { return p.cls; })`): the build reports a located `Cannot compose` error. A condition choosing between known classes or rule objects is supported.

Inside a template, an interpolation standing where a declaration would is a mixin: `${mixin}` and `${(p) => p.active && mixin}` compose their class with the component's. A literal or constant is written into the CSS wherever it stands — a value, a CSS snippet, a selector. Any other interpolation in a selector or a property name is a build error, as are runtime values in `css`, `keyframes` and global styles, which have no element to set a CSS variable on.

`.attrs()` and `.withConfig()` chain onto any factory. Attrs are merged over the props in order, as styled-components does — an object is spread, a function is called with the props. In `.withConfig()`, `shouldForwardProp` is evaluated at build time, and `componentId` gives the element the classes styled-components gives it, so CSS written elsewhere can select it: the id, or `displayName-componentId` when both are set (with `displayName` escaped as styled-components escapes it), split at whitespace. An empty or blank id adds no class. A component extending it renders those classes too, and the component's `styledComponentId` is that id. Emotion's `target` option likewise adds `String(target)` to the classes, split the same way, so `''` adds none and `undefined` leaves the option unset. As in Emotion, those classes belong to the component alone: `styled(Card)` renders `Card`'s styles without them, wherever `Card` is defined, while `Card.withComponent('a')` keeps them. A compiled component with a `target` holds itself without it as `__devupBase`, which an extension renders in its place when the build cannot see where the component comes from, as Emotion composes through `__emotion_base`. When several `.withConfig()` calls set an option, the last one wins. A value only the runtime knows is a build error, as is a `componentId` that is not a string, which styled-components throws on. A string `displayName` in `.withConfig()`, or Emotion's `label` option, becomes the component's `displayName`, as each library sets it for React DevTools; Devup UI does not add it to the class names, and a `label:` declaration in CSS text is ignored:

```tsx
const Button = styled.button
  .attrs({ type: 'button' })
  .attrs((props) => ({ disabled: props.loading }))
  .withConfig({ displayName: 'Button' })`
  color: red;
`
```

A file may import `styled` from several of these libraries at once; every import compiles.

Namespace imports work too. `@emotion/styled` and `styled-components` export a single callable, so the namespace binding _is_ that value and it is bound straight to the Devup UI export:

```tsx
import * as Emotion from '@emotion/styled'
// → import { styled as Emotion } from '@devup-ui/react'

const Card = Emotion.div`color: red;`
```

A component selector matches the elements each library matches. A selected component carries a short marker class, and `${Card}` selects it. Under styled-components, `styled(Card)` keeps `Card`'s class, so `${Card}` matches the extension too. Emotion's selector reads `Card`'s `target`, which `styled(Card)` renders without, so a component made with Emotion's `styled` keeps its marker to itself, as it does a `target`. The marker stays on `Card.withComponent('a')`, which keeps `Card`'s options. Under Emotion, `Card.withComponent('a')` shares `Card`'s marker instead of taking its own, even when it is exported or selected: `${Link}` for `Link = Card.withComponent('a')` matches `Card` and every `withComponent` result of it, and `styled(Link)`, like `styled(Card)`, renders without the marker.

`withComponent` renders the component's styles as another tag or component. The build compiles it when it reads the component, in the same module or another one. A component compiled from Emotion's `styled` also takes `withComponent` at runtime, as Emotion's components do, so the call works where the build cannot see the component, or when only the runtime knows the target (`Card.withComponent(pick())`). That component renders the tag through `as`, which a later `as` still replaces, and keeps the classes the component's `target` gives. Options passed beside the target are a build error, because they would change classes and props the build cannot see. Create that component with `styled(tag, options)` instead.

## Props passed to the element

Each library's components pass props on as that library does. A component made with styled-components' `styled` follows styled-components v6, which no longer filters props: without `shouldForwardProp`, every prop reaches what it renders, a tag included, even one its styles read, such as `tone` below. Only `$` props, `as` (and `forwardedAs`, which becomes the rendered element's `as`) and `theme` stay behind. A component made with Emotion's `styled` keeps the props its styles read off a tag unless the tag takes them as attributes, as Emotion's `@emotion/is-prop-valid` check does.

```tsx
import styled from 'styled-components'

const Badge = styled.span`
  color: ${(p) => p.tone};
  background: ${(p) => p.$surface};
`

// <span tone="teal" class="..."> — `tone` reaches the DOM, as in styled-components v6
const badge = <Badge $surface="white" tone="teal" />
```

React warns about a prop the DOM does not know, as it does under styled-components. To keep a prop off the element, start its name with `$`, or give the component its own `shouldForwardProp` through `.withConfig()`, which the build evaluates. A component extending another applies both predicates, so a prop passes only when both pass it, and when several `.withConfig()` calls set `shouldForwardProp` on one component, the last one wins:

```tsx
const Badge = styled.span.withConfig({
  shouldForwardProp: (prop) => prop !== 'tone',
})`
  color: ${(p) => p.tone};
`
```

The build evaluates the predicate and adds no code that runs it, so it decides only the props the build can name: those the component's styles and attrs read, those the predicate names (`prop === 'tone'`, `['a', 'b'].includes(prop)`), and the attributes written on an element using the component. styled-components and Emotion call it at runtime for every prop, so this is a known difference: a prop the build never sees by name, such as one a spread passes or a caller adds, reaches the element even when the predicate would reject it (`() => false` still passes a spread `id`). Keep such props off the element with `$` transient props or by not passing them. Under styled-components the second argument is the element the component renders, and the build reads `typeof element === 'string'` from the target the component is declared with, so `as` choosing another element does not change it. Calling the second argument as styled-components v5's validator (`(prop, valid) => valid(prop)`) fails in v6, so it is a build error: call `isPropValid` from `@emotion/is-prop-valid` instead. Emotion's `shouldForwardProp` takes the prop name alone.

```tsx
import isPropValid from '@emotion/is-prop-valid'
import styled from 'styled-components'

const Card = styled.div.withConfig({
  shouldForwardProp: (prop, element) =>
    typeof element !== 'string' || isPropValid(prop),
})`
  color: ${(p) => p.tone};
`

// Devup UI keeps `tone`, which the styles read, off the <div>, as styled-components
// does. `customPayload` reaches it: only the runtime sees that name.
const card = <Card customPayload="x" id="a" tone="teal" />
```

`StyleSheetManager` is accepted but inert, so a `shouldForwardProp` given to it is never applied. Since it would filter the props of every styled component below it, which the compiled components cannot see, it is a build error rather than being silently dropped. Code that restores styled-components v5 filtering with `<StyleSheetManager shouldForwardProp={isPropValid}>` must move that filter onto the components: rename the styling props to `$` props, or give each component `.withConfig({ shouldForwardProp })`.

## Transient props

Props whose names start with `$` are transient, as in styled-components: style functions read them, but a styled component never passes them on to what it renders — a tag, a component or what `as` names. That includes `$` props a runtime spread brings and those attrs create, even when `shouldForwardProp` allows them:

```tsx
const Title = styled.h1`
  color: ${(p) => p.$tone};
`

function Heading(props) {
  return <Title {...props} />
}

// `$tone` sets the color; the <h1> gets `id` but neither `$tone` nor `$track`
const heading = <Heading $tone="teal" $track="hero" id="intro" />
```

## Theme interpolation

`ThemeProvider` redefines the CSS variables its theme changes on a `display: contents` `<div>`, so it scopes the theme to its subtree without touching layout (the element still counts for `>` selectors and inside `<table>` or `<select>`; see [limitations](/docs/limitations)). The outermost provider also declares the whole theme on `:root`, so `createGlobalStyle` rules on `html` or `body` read the theme too. Interpolations that read the theme are resolved at build time — no runtime lookup:

```tsx
const Card = styled.div`
  color: ${(p) => p.theme.brand};
  border: 1px solid ${({ theme }) => theme.colors.line};
`
```

```css
.a {
  color: var(--brand);
}
.b {
  border: 1px solid var(--colors-line);
}
```

Because those reads are CSS variables, a `theme` prop on one element (`<Card theme={{ brand: 'teal' }} />`) cannot change them, so it is a build error on a component whose styles read the theme: wrap the element in a `ThemeProvider` with that theme instead. A component that does not read the theme drops the prop, as before.

Nested themes flatten with a hyphen, so `theme.colors.line` and `--colors-line` always agree. The object form resolves identically:

```tsx
const Card = styled('div')({ color: (p) => p.theme.brand })
```

Reading the theme in JS gives the same references back:

```tsx
import { useTheme } from 'styled-components'

function Divider() {
  const theme = useTheme()
  // `${theme.colors.line}` === 'var(--colors-line)'
  return <hr style={{ borderColor: `${theme.colors.line}` }} />
}
```

## Global styles

`createGlobalStyle` keeps its render site — the rules are lifted into the stylesheet and the call collapses to a component that renders nothing:

```tsx
const GlobalStyle = createGlobalStyle`body { margin: 0; }`
// → const GlobalStyle = () => null
```

Emotion's `<Global styles={...} />` behaves the same way: the `styles` prop is extracted and the element stops rendering markup. `styles` takes an object of rules by selector, a `css()` class holding rules under selectors (`` css`body { margin: 0; }` ``), an array of those (`false`, `null` and `undefined` entries are skipped), or a function of the theme, whose `theme.a.b` reads become `var(--a-b)`. A class with declarations of its own, a spread in the array and any other read of the theme are build errors.

A styled component compiles to a function component, whose `defaultProps` React 19 ignores, so `Button.defaultProps = { ... }` is a build error: give the default where the prop is read (`${(p) => p.$tone ?? 'red'}`) or pass the prop where the component is rendered.

## The rest of the surface

| API                                      | Result                                                                           |
| ---------------------------------------- | -------------------------------------------------------------------------------- |
| `css`, `keyframes`                       | Devup UI equivalents                                                             |
| `ThemeProvider`, `useTheme`, `withTheme` | `@devup-ui/react/compat`, CSS-variable backed                                    |
| `createGlobalStyle`, `Global`            | extracted, render nothing                                                        |
| `ServerStyleSheet`, `StyleSheetManager`  | inert — Devup UI already emits a real stylesheet, so there is nothing to collect |
| `CacheProvider`                          | renders its children; the cache it configures has nothing to hold                |
| `isStyledComponent`                      | `true` for components compiled from `styled`, marked with `styledComponentId`    |
| `css` prop, `jsx`, JSX runtime pragmas   | compiled to `className` and `style`                                              |
| `ClassNames`                             | replaced by what its child renders, each `css` / `cx` call compiled to classes   |
| Component selectors (`${Child}`)         | a marker class; Emotion extensions render without it, as Emotion's do            |
| Markers no module selects                | dropped by one-shot Vite and webpack production builds                           |
| `.attrs()`, `.withConfig()`              | attrs merged over props; build-time `shouldForwardProp`; `componentId` classes   |

## Limitations

Composition only the runtime sees — a `className` from props, an external class, a `styled()` base the build cannot read — follows CSS specificity and stylesheet order rather than the order you wrote. Styled components and classes defined in another module are not read as build-time values, `stylisPlugins` given to `StyleSheetManager` or `createCache()` and `StyleSheetManager`'s `shouldForwardProp` and `namespace` are build errors, and test utilities and React Native targets are not supported. A component of your own that takes the `css` prop must pass on both `className` and `style`. See [Supported Syntax & Limitations](/docs/limitations) for the full list.
