# styled-components & Emotion

두 라이브러리 모두 같은 기본 alias로 처리되며, `styled`를 어떤 형태로 작성하든 정적 컴포넌트로 컴파일됩니다.

## 지원하는 호출 형태

```tsx
import styled from 'styled-components'

const A = styled.div`
  color: red;
`
const B = styled('div')`
  color: red;
`
const C = styled.div({ bg: 'red' })
const D = styled('div')({ bg: 'red' })
const E = styled(Component)({ bg: 'red' })
const F = styled('div', { bg: 'red' })
const G = styled(motion.div)`
  color: red;
`
const H = styled(forwardRef(Field))({ bg: 'red' })
const I = styled['div']`
  color: red;
`
```

태그, 컴포넌트, `motion.div` 같은 멤버, 그 밖의 어떤 값이든 base로 렌더링할 수 있으며, base는 컴포넌트가 선언된 위치에서 한 번 읽힙니다. 태그는 `styled['div']`나 ``styled[`div`]``처럼 리터럴 키로도 읽을 수 있으며, `.attrs`와 `.withConfig`를 포함해 `styled.div`와 같은 결과를 만듭니다. 빌드가 읽을 수 없는 키(`styled[tag]`)나 `styled.` 뒤에 쓸 수 없는 키(`styled['my-element']`)는 빌드 에러입니다. `null`, 숫자, 불리언, `undefined`는 렌더링되지 않으므로 빌드 에러이며, 컴파일되지 않은 채 남은 `styled`(스타일을 받지 않은 `styled('div')`, 그대로 export된 `styled.div`)도 마찬가지입니다. 그 import는 제거되므로 해당 코드는 런타임에 에러를 던지게 됩니다.

같은 파일의 `const`에 담긴 `keyframes`나 `css` 결과는 빌드 타임 값이므로 `` css`animation: ${fadeIn} 1s;` ``와 `styled.div({ ['.' + card + ':hover &']: { margin: 0 } })`가 동작합니다. CSS 텍스트에서 선언이 올 자리에 놓인 클래스는 mixin이며, 컴포넌트의 클래스와 합성됩니다. 다른 모듈에서 import한 값은 그렇지 않습니다. 그 이름은 해당 파일이 빌드된 뒤에야 알 수 있으므로, 사용하는 곳에서 선언하세요.

객체 스타일은 라이브러리의 동작을 따릅니다. 여러 스타일 인자나 그 배열은 하나의 규칙 집합으로 병합되며, 나중 선언이 앞선 선언을 대체하고 중첩 규칙은 병합됩니다. Emotion의 옵션 인자(`styled('div', { shouldForwardProp })(...)`)도 허용되며, 그 `shouldForwardProp`은 빌드 타임에 평가됩니다. 숫자는 Emotion과 styled-components에서처럼 픽셀을 의미합니다. `padding: 8`은 `8px`이고, `lineHeight` 같은 단위 없는 속성은 작성한 그대로 유지됩니다. 반면 `p` 같은 Devup UI 축약형은 spacing 스케일을 유지합니다.

속성 값으로 쓰인 배열도 Devup UI의 브레이크포인트가 아니라 라이브러리의 동작을 따릅니다. Emotion에서는 각 값을 차례로 fallback으로 선언하며(`height: ['100vh', '100dvh']`는 `height:100vh;height:100dvh`), `null`, `undefined`, boolean은 건너뜁니다. 첫 번째 값이 문자열이 아니면 Emotion은 유효한 선언을 만들지 않으므로(`margin: [4]`) 아무것도 선언되지 않습니다. styled-components는 값들을 쉼표로 이어 하나의 선언으로 작성합니다(`fontFamily: ['Arial', 'sans-serif']`는 `font-family:Arial,sans-serif`). `p` 같은 Devup UI 축약 속성은 계속 배열을 브레이크포인트로 읽으며, `@devup-ui/react`의 `css()`도 마찬가지입니다.

스타일 속성을 이름으로 갖지 않는 객체를 담은 키는 라이브러리에서처럼 중첩 선택자입니다. `{ span: { color: 'blue' } }`는 `.a span{color:blue}`가 되고, `{ 'h1, h2': { margin: 0 } }`는 `.b h1`과 `.b h2`를 만들며, `:`, `::`, `[`로 시작하는 키는 컴포넌트 자체에 적용되고, `&`는 컴포넌트가 들어갈 위치를 나타냅니다. `hover`나 `before`처럼 단독으로 쓴 의사 클래스나 의사 요소 이름은 `<hover>` 요소가 아니라 Devup UI의 [`selectors`](/docs/api/selector)에서처럼 해당 선택자이며, `p` 같은 Devup UI 축약형은 속성으로 유지되므로 문단을 선택하려면 `'& p'`로 작성하세요.

스타일 인자는 조건부일 수 있습니다. `css`에서와 마찬가지로 `styled`에서도 `cond && { ... }`, `cond ? { ... } : { ... }`, `value || { ... }`, `value ?? { ... }`를 쓸 수 있습니다. 여기서 설정하는 각 속성은 앞선 값에 대한 속성별 삼항식(`color: cond ? 'blue' : 'red'`)이 되므로, 결과는 atomic 클래스가 스타일시트에 놓이는 순서에 좌우되지 않습니다. 조건부 클래스는 `cond ? cls : ''`로 합쳐지며, `||` / `??`의 왼쪽은 문자열일 때만 합쳐집니다. 라이브러리가 그 밖의 값은 건너뛰기 때문입니다. 규칙 객체 옆에 전달한 클래스는 `css`에서와 마찬가지로 `styled`에서도 합성됩니다.

빌드 타임에 알 수 없는 스타일 인자(빌드가 실행할 수 없는 함수 호출, 계산할 수 없는 spread나 computed key)는 스타일이 조용히 누락되는 대신 그 대상을 명시하는 빌드 에러가 됩니다. 모듈이 계산하는 spread, 선택자 값, computed key(`styled.div({ ...cardStyles(), _hover: hoverStyles })`)는 계산되며, 그 밖의 값은 런타임에 설정되는 CSS 변수로 남습니다. 파일에 선언했거나 import한 객체 상수는 그 자리에 직접 작성한 것처럼 읽힙니다: `styled.div(baseStyles)`, `styled.div({ ...baseStyles, color: 'red' })`. 규칙 객체가 아닌 단일 인자는 여러 인자일 때와 마찬가지로 클래스로 합성되며, 모듈이 계산하는 규칙을 담은 인자(`const base = makeStyles()`, `styled.div(base)`)는 그 규칙을 적용합니다. 객체 형태에서 값은 테마를 읽을 수 있지만(`(p) => p.theme.brand`), props에 대한 그 밖의 함수는 빌드 에러입니다. 이런 함수는 템플릿(`${(p) => p.color}`)으로 작성하세요. 템플릿에서는 CSS 변수가 됩니다.

styled 콜백은 런타임에만 알 수 있는 클래스 이름을 반환할 수 없습니다(`styled.div(p => { return p.cls; })`). 이 경우 빌드는 위치가 표시된 `Cannot compose` 에러를 보고합니다. 알려진 클래스나 규칙 객체 중에서 고르는 조건은 지원합니다.

템플릿 안에서 선언이 올 자리에 놓인 interpolation은 mixin입니다. `${mixin}`과 `${(p) => p.active && mixin}`은 자신의 클래스를 컴포넌트의 클래스와 합성합니다. 리터럴이나 상수는 값, CSS 조각, 선택자 등 어디에 놓이든 CSS에 그대로 작성됩니다. 선택자나 속성 이름 안의 그 밖의 interpolation은 빌드 에러이며, `css`, `keyframes`, 전역 스타일 안의 런타임 값도 마찬가지입니다. 이들에는 CSS 변수를 설정할 요소가 없기 때문입니다.

`.attrs()`와 `.withConfig()`는 어떤 factory에도 체이닝할 수 있습니다. attrs는 styled-components처럼 순서대로 props 위에 병합되며, 객체는 spread되고 함수는 props를 인자로 호출됩니다. `.withConfig()`에서 `shouldForwardProp`은 빌드 타임에 평가되며, `componentId`는 styled-components가 부여하는 클래스를 요소에 부여하므로 다른 곳에서 작성한 CSS가 그 요소를 선택할 수 있습니다. 그 클래스는 id이며, 둘 다 설정된 경우 `displayName-componentId`(`displayName`은 styled-components와 같은 방식으로 escape됩니다)이고, 공백을 기준으로 나뉩니다. 비어 있거나 공백뿐인 id는 클래스를 추가하지 않습니다. 이 컴포넌트를 확장하는 컴포넌트도 그 클래스를 렌더링하며, 컴포넌트의 `styledComponentId`는 그 id입니다. Emotion의 `target` 옵션도 마찬가지로 `String(target)`을 클래스에 추가하고 같은 방식으로 나뉘므로, `''`는 아무것도 추가하지 않고 `undefined`는 옵션을 설정하지 않은 상태로 둡니다. Emotion에서처럼 이 클래스는 해당 컴포넌트에만 속합니다. `styled(Card)`는 `Card`가 어디에 정의되어 있든 그 클래스 없이 `Card`의 스타일을 렌더링하며, `Card.withComponent('a')`는 클래스를 유지합니다. `target`이 있는 컴파일된 컴포넌트는 `target`이 없는 자기 자신을 `__devupBase`로 보관하며, 빌드가 컴포넌트의 출처를 볼 수 없을 때 확장 컴포넌트는 그 자리에 이를 렌더링합니다. Emotion이 `__emotion_base`를 통해 합성하는 것과 같습니다. 여러 `.withConfig()` 호출이 같은 옵션을 설정하면 마지막 호출이 적용됩니다. 런타임에만 알 수 있는 값은 빌드 에러이며, 문자열이 아닌 `componentId`도 마찬가지입니다. styled-components는 이 경우 에러를 던집니다. `.withConfig()`의 문자열 `displayName`이나 Emotion의 `label` 옵션은 각 라이브러리가 React DevTools용으로 설정하듯 컴포넌트의 `displayName`이 됩니다. Devup UI는 이를 클래스 이름에 추가하지 않으며, CSS 텍스트의 `label:` 선언은 무시됩니다:

```tsx
const Button = styled.button
  .attrs({ type: 'button' })
  .attrs((props) => ({ disabled: props.loading }))
  .withConfig({ displayName: 'Button' })`
  color: red;
`
```

한 파일에서 여러 라이브러리의 `styled`를 동시에 import할 수 있으며, 모든 import가 컴파일됩니다.

네임스페이스 import도 동작합니다. `@emotion/styled`와 `styled-components`는 호출 가능한 값 하나를 export하므로, 네임스페이스 바인딩이 _곧_ 그 값이며 Devup UI export에 바로 바인딩됩니다:

```tsx
import * as Emotion from '@emotion/styled'
// → import { styled as Emotion } from '@devup-ui/react'

const Card = Emotion.div`color: red;`
```

컴포넌트 선택자는 각 라이브러리가 매칭하는 요소를 매칭합니다. 선택되는 컴포넌트는 짧은 marker 클래스를 가지며, `${Card}`는 그 클래스를 선택합니다. styled-components에서는 `styled(Card)`가 `Card`의 클래스를 유지하므로 `${Card}`가 확장 컴포넌트도 매칭합니다. Emotion의 선택자는 `Card`의 `target`을 읽는데, `styled(Card)`는 이를 제외하고 렌더링하므로 Emotion의 `styled`로 만든 컴포넌트는 `target`과 마찬가지로 marker를 자기 자신에만 둡니다. marker는 `Card`의 옵션을 유지하는 `Card.withComponent('a')`에도 남습니다. Emotion에서 `Card.withComponent('a')`는 export되거나 선택되는 경우에도 자체 marker를 갖는 대신 `Card`의 marker를 공유합니다. `Link = Card.withComponent('a')`일 때 `${Link}`는 `Card`와 그 모든 `withComponent` 결과를 매칭하며, `styled(Link)`는 `styled(Card)`처럼 marker 없이 렌더링됩니다.

`withComponent`는 컴포넌트의 스타일을 다른 태그나 컴포넌트로 렌더링합니다. 빌드는 같은 모듈이든 다른 모듈이든 컴포넌트를 읽을 때 이를 컴파일합니다. Emotion의 `styled`로 컴파일된 컴포넌트는 Emotion의 컴포넌트처럼 런타임에도 `withComponent`를 받으므로, 빌드가 컴포넌트를 볼 수 없는 곳이나 런타임에만 대상을 알 수 있는 경우(`Card.withComponent(pick())`)에도 호출이 동작합니다. 그 컴포넌트는 `as`를 통해 태그를 렌더링하며, 이후의 `as`가 여전히 이를 대체할 수 있고, 컴포넌트의 `target`이 부여하는 클래스를 유지합니다. 대상 옆에 전달한 옵션은 빌드가 볼 수 없는 클래스와 props를 바꾸게 되므로 빌드 에러입니다. 이런 컴포넌트는 대신 `styled(tag, options)`로 만드세요.

## 요소에 전달되는 props

각 라이브러리의 컴포넌트는 해당 라이브러리와 같은 방식으로 props를 전달합니다. styled-components의 `styled`로 만든 컴포넌트는 더 이상 props를 필터링하지 않는 styled-components v6를 따릅니다. `shouldForwardProp`이 없으면 모든 prop이 렌더링 대상에 전달되며, 태그도 포함되고 아래의 `tone`처럼 스타일이 읽는 prop도 마찬가지입니다. `$` props, `as`(그리고 렌더링되는 요소의 `as`가 되는 `forwardedAs`), `theme`만 전달되지 않습니다. Emotion의 `styled`로 만든 컴포넌트는 Emotion의 `@emotion/is-prop-valid` 검사처럼, 태그가 속성으로 받지 않는 한 스타일이 읽는 props를 태그에 전달하지 않습니다.

```tsx
import styled from 'styled-components'

const Badge = styled.span`
  color: ${(p) => p.tone};
  background: ${(p) => p.$surface};
`

// <span tone="teal" class="..."> — `tone` reaches the DOM, as in styled-components v6
const badge = <Badge $surface="white" tone="teal" />
```

React는 styled-components에서와 마찬가지로 DOM이 모르는 prop에 대해 경고합니다. prop을 요소에 전달하지 않으려면 이름을 `$`로 시작하거나, `.withConfig()`로 컴포넌트에 자체 `shouldForwardProp`을 지정하세요. 빌드가 이를 평가합니다. 다른 컴포넌트를 확장하는 컴포넌트는 두 predicate를 모두 적용하므로 둘 다 통과시킬 때만 prop이 전달되며, 한 컴포넌트에서 여러 `.withConfig()` 호출이 `shouldForwardProp`을 설정하면 마지막 호출이 적용됩니다:

```tsx
const Badge = styled.span.withConfig({
  shouldForwardProp: (prop) => prop !== 'tone',
})`
  color: ${(p) => p.tone};
`
```

`StyleSheetManager`는 허용되지만 아무 동작도 하지 않으므로, 여기에 전달한 `shouldForwardProp`은 적용되지 않습니다. 이는 그 아래의 모든 styled 컴포넌트의 props를 필터링하게 되는데 컴파일된 컴포넌트는 이를 볼 수 없으므로, 조용히 무시되는 대신 빌드 에러가 됩니다. `<StyleSheetManager shouldForwardProp={isPropValid}>`로 styled-components v5의 필터링을 되살리는 코드는 그 필터를 컴포넌트로 옮겨야 합니다. 스타일링 props의 이름을 `$` props로 바꾸거나, 각 컴포넌트에 `.withConfig({ shouldForwardProp })`를 지정하세요.

## Transient props

이름이 `$`로 시작하는 props는 styled-components에서처럼 transient입니다. 스타일 함수는 이를 읽지만, styled 컴포넌트는 렌더링 대상(태그, 컴포넌트, `as`가 지정한 대상)에 이를 전달하지 않습니다. 런타임 spread로 들어온 `$` props와 attrs가 만든 `$` props도 `shouldForwardProp`이 허용하더라도 마찬가지입니다:

```tsx
const Title = styled.h1`
  color: ${(p) => p.$tone};
`

function Heading(props) {
  return <Title {...props} />
}

// `$tone` sets the color; the <h1> gets `id` but neither `$tone` nor `$track`
const heading = <Heading $tone="teal" $track="hero" id="intro" />
```

## 테마 interpolation

`ThemeProvider`는 테마가 바꾸는 CSS 변수를 `display: contents` `<div>`에 다시 정의하므로, 레이아웃에 영향을 주지 않고 테마를 하위 트리로 한정합니다(이 요소는 `>` 선택자와 `<table>`이나 `<select>` 내부에서는 여전히 요소로 취급됩니다. [제한 사항](/docs/limitations)을 참고하세요). 가장 바깥쪽 provider는 전체 테마를 `:root`에도 선언하므로, `html`이나 `body`에 대한 `createGlobalStyle` 규칙도 테마를 읽습니다. 테마를 읽는 interpolation은 빌드 타임에 해석되며, 런타임 조회는 없습니다:

```tsx
const Card = styled.div`
  color: ${(p) => p.theme.brand};
  border: 1px solid ${({ theme }) => theme.colors.line};
`
```

```css
.a {
  color: var(--brand);
}
.b {
  border: 1px solid var(--colors-line);
}
```

이 값들은 CSS 변수이므로 한 요소의 `theme` prop(`<Card theme={{ brand: 'teal' }} />`)으로는 바꿀 수 없습니다. 따라서 스타일이 테마를 읽는 컴포넌트에서는 빌드 에러가 되며, 대신 해당 테마를 가진 `ThemeProvider`로 요소를 감싸세요. 테마를 읽지 않는 컴포넌트는 이전과 같이 이 prop을 버립니다.

중첩된 테마는 하이픈으로 평탄화되므로 `theme.colors.line`과 `--colors-line`은 항상 일치합니다. 객체 형태도 동일하게 해석됩니다:

```tsx
const Card = styled('div')({ color: (p) => p.theme.brand })
```

JS에서 테마를 읽으면 같은 참조가 반환됩니다:

```tsx
import { useTheme } from 'styled-components'

function Divider() {
  const theme = useTheme()
  // `${theme.colors.line}` === 'var(--colors-line)'
  return <hr style={{ borderColor: `${theme.colors.line}` }} />
}
```

## 전역 스타일

`createGlobalStyle`은 렌더링 위치를 유지합니다. 규칙은 스타일시트로 옮겨지고, 호출은 아무것도 렌더링하지 않는 컴포넌트로 축소됩니다:

```tsx
const GlobalStyle = createGlobalStyle`body { margin: 0; }`
// → const GlobalStyle = () => null
```

Emotion의 `<Global styles={...} />`도 같은 방식으로 동작합니다. `styles` prop이 추출되고 요소는 마크업을 렌더링하지 않습니다. `styles`는 선택자별 규칙 객체, 선택자 아래에 규칙을 담은 `css()` 클래스(`` css`body { margin: 0; }` ``), 이들의 배열(`false`, `null`, `undefined` 항목은 건너뜁니다), 또는 테마를 받는 함수를 받으며, 함수의 `theme.a.b` 읽기는 `var(--a-b)`가 됩니다. 자체 선언을 가진 클래스, 배열 안의 spread, 그 밖의 테마 읽기는 빌드 에러입니다.

styled 컴포넌트는 함수 컴포넌트로 컴파일되며 React 19는 함수 컴포넌트의 `defaultProps`를 무시하므로, `Button.defaultProps = { ... }`는 빌드 에러입니다. prop을 읽는 곳에서 기본값을 지정하거나(`${(p) => p.$tone ?? 'red'}`) 컴포넌트를 렌더링하는 곳에서 prop을 전달하세요.

## 그 밖의 API

| API                                      | 결과                                                                            |
| ---------------------------------------- | ------------------------------------------------------------------------------- |
| `css`, `keyframes`                       | Devup UI의 대응 API                                                             |
| `ThemeProvider`, `useTheme`, `withTheme` | `@devup-ui/react/compat`, CSS 변수 기반                                         |
| `createGlobalStyle`, `Global`            | 추출되며 아무것도 렌더링하지 않음                                               |
| `ServerStyleSheet`, `StyleSheetManager`  | 동작 없음 — Devup UI는 이미 실제 스타일시트를 출력하므로 수집할 것이 없음       |
| `CacheProvider`                          | children을 렌더링함. 설정하는 캐시에는 담을 것이 없음                           |
| `isStyledComponent`                      | `styled`로 컴파일되어 `styledComponentId`가 표시된 컴포넌트에 대해 `true`       |
| `css` prop, `jsx`, JSX runtime pragma    | `className`과 `style`로 컴파일됨                                                |
| `ClassNames`                             | child가 렌더링하는 결과로 대체되며, 각 `css` / `cx` 호출은 클래스로 컴파일됨    |
| 컴포넌트 선택자(`${Child}`)              | marker 클래스. Emotion의 확장 컴포넌트는 Emotion에서처럼 이를 제외하고 렌더링함 |
| `.attrs()`, `.withConfig()`              | attrs는 props 위에 병합됨. 빌드 타임 `shouldForwardProp`. `componentId` 클래스  |

## 제한 사항

런타임에만 보이는 합성(props로 받은 `className`, 외부 클래스, 빌드가 읽을 수 없는 `styled()` base)은 작성한 순서가 아니라 CSS 명시도와 스타일시트 순서를 따릅니다. 다른 모듈에 정의된 styled 컴포넌트와 클래스는 빌드 타임 값으로 읽히지 않으며, `StyleSheetManager`나 `createCache()`에 전달한 `stylisPlugins`와 `StyleSheetManager`의 `shouldForwardProp`, `namespace`는 빌드 에러이고, 테스트 유틸리티와 React Native 타깃은 지원하지 않습니다. `css` prop을 받는 직접 만든 컴포넌트는 `className`과 `style`을 모두 전달해야 합니다. 전체 목록은 [지원 문법 및 제한 사항](/docs/limitations)을 참고하세요.
